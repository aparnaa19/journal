# Password spraying detection with splunk
display_title: What is password spraying
skills: Log analysis, Threat hunting, SPL, Regex field extraction, Splunk data onboarding, Windows event log analysis, Incident analysis, MITRE ATT&CK mapping
tools: Splunk Enterprise, Windows Security Event Logs, MITRE ATT&CK, Splunk attack_data

**Brute Force Password Spraying Detection with Splunk**</p><p>In this lab, I looked at Windows Security logs from a domain controller and found a password spraying attack. This time Splunk could not read the logs at first, so before I could search anything, I had to make Splunk how to read them.</p><p>In this lab:</p><ul><li>loaded Windows Security logs and created my own source type so Splunk could read them</li><li>worked out what normal activity looks like on a domain controller</li><li>found the failed logins and worked out what kind of attack it was</li><li>checked whether any of the attempts worked</li></ul><h3>What is password spraying</h3><ul><li>Password spraying (MITRE <strong>T1110.003</strong>) is when an attacker tries one common password on many different accounts, once each</li><li>They only try once or twice per account, so the accounts don't get locked</li><li>I think of it as trying one key on every door in a building, instead of trying lots of keys on one door</li><li>Trying lots of keys on one door is password guessing (T1110.001), which I did in my last lab. The difference is just the shape:</li></ul><h3>About the logs</h3><p>The logs come from Splunk's public attack_data repository on GitHub (datasets/attack_techniques/T1110.003/purplesharp_remote_spray). They were recorded in a test Windows network called attackrange.local in April 2021, while a tool called PurpleSharp ran a password spraying attack.</p><p>The file has 162 events from one domain controller, <strong>win-dc-697</strong>. A domain controller is the server that checks everyone's username and password in a Windows network.</p><h3>Getting the logs into Splunk</h3><h4>Step 1: I uploaded the file</h4><p>I used <strong>Settings → Add Data → Upload</strong> and picked the file.</p><p><img src="media/password-spraying-detection-with-splunk-1.png" /></p><h4>Step 2: Splunk could not read it</h4><p>On the Set Source Type page, I used the default source type, and the preview showed warning icons</p><p><img src="media/password-spraying-detection-with-splunk-2.png" /></p><ul><li><strong>"Could not use regex to parse timestamp"</strong> means Splunk couldn't read the date, so it gave every event today's date</li><li><strong>"Breaking event because limit of 256 has been exceeded"</strong> means Splunk couldn't find where one event ends. By default it starts a new event when it sees a date, but it couldn't read the date. So it kept joining lines until it hit 256 lines, then gave up and made every line its own event</li></ul><p>So the two problems were linked: the broken date caused the broken event splitting. Splunk doesn't have a Windows source type built in (it comes with a separate add-on), so I decided to create my own.</p><h4>Step 3: I looked at the raw file first</h4><p>Before changing any settings, I opened the file in Notepad to see what one event looks like.</p><p><img src="media/password-spraying-detection-with-splunk-3.png" /></p><ul><li>Every event starts with a date line, like 04/20/2021 09:07:40 PM</li><li>The top of each event is written as key=value (EventCode=4624). Splunk turns these into fields automatically</li><li>The rest is written as Name: value (Account Name: WIN-HOST-816$). Splunk does not turn these into fields, so I have to pull them out myself with rex</li></ul><h4>Step 4: I told Splunk where each event starts</h4><p>Under <strong>Event Breaks</strong>, I chose <strong>Regex</strong> and gave Splunk the shape of the date line:</p><p>([\r\n]+)\d{2}/\d{2}/\d{4} \d{2}:\d{2}:\d{2} [AP]M</p><ul><li>([\r\n]+) is the line break. Splunk cuts the file here</li><li>\d{2} means two digits, and \d{4} means four digits</li><li>[AP]M means AM or PM</li></ul><p>So it means: start a new event wherever a new line begins with a date.</p><p>My first tries didn't work. Splunk still showed one giant event of 287 lines, because I had a missing backslash, an extra colon, and a backslash in front of [AP].</p><p><img src="media/password-spraying-detection-with-splunk-4.png" /></p><p>I learned that regex has to copy the log exactly, character by character. A backslash in front of a letter (\d) makes it special, but a backslash in front of a bracket (\[) makes it a normal character.</p><h4>Step 5: I told Splunk how to read the date</h4><p>Under <strong>Timestamp → Advanced</strong>, I set the format:</p><p>%m/%d/%Y %I:%M:%S %p</p><p><img src="media/password-spraying-detection-with-splunk-5.png" /></p><ul><li>%m/%d/%Y is month/day/year</li><li>%I is the hour on a 12-hour clock, and %p is AM or PM</li></ul><p>I used %I instead of %H because the log has PM in it. With %H (24-hour clock), every evening event would be 12 hours off.</p><h4>Step 6: One more warning, the logs were too old</h4><p><img src="media/password-spraying-detection-with-splunk-6.png" /></p><p>This time Splunk read the date correctly (it turned 09:07:40 PM into 21:07:40), but it rejected it. By default Splunk ignores dates older than about 2,000 days, and April 2021 was just over that. My SSH and Azure logs were newer, so I had never seen this before.</p><p>I fixed it under <strong>Advanced</strong> by adding a new setting, MAX_DAYS_AGO = 3650 (10 years).</p><p><img src="media/password-spraying-detection-with-splunk-7.png" /></p><h4>Step 7: It worked</h4><p><img src="media/password-spraying-detection-with-splunk-8.png" /></p><p>Now every event started with its date line, the time showed 4/20/21, the warnings were gone, and there were 162 events.</p><h4>Step 8: I saved my source type</h4><p><img src="media/password-spraying-detection-with-splunk-9.png" /></p><p>I named it <strong>WinEventLog:Security</strong>. </p><h4>Step 9: I created an index and finished the upload</h4><p><img src="media/password-spraying-detection-with-splunk-10.png" /></p><p>I made a new index called <strong>bruteforce_windows</strong>. </p><p><img src="media/password-spraying-detection-with-splunk-11.png" /></p><p><img src="media/password-spraying-detection-with-splunk-12.png" /></p><p>The host field shows my laptop's name, because host is the machine that uploaded the file into Splunk. The real machine names are inside the logs.</p><h3>Investigating the logs</h3><h4>How I approached it</h4><p>I asked 5 questions I can use on any log, and named the attack at the end:</p><ol><li><strong>What am I looking at?</strong> Which machine, what time period, how much data</li><li><strong>What is normal here?</strong> What makes up most of the activity</li><li><strong>What doesn't fit?</strong> Failures, rare events, sudden bursts</li><li><strong>Follow the thread.</strong> Who, which accounts, from where, did it work?</li><li><strong>So what?</strong> Is it an attack, and what should be done?</li></ol><h4>Step 1: What am I looking at?</h4><p>I searched index="bruteforce_windows" and read the field panel on the left. The number next to each field is how many different values it has.</p><p><img src="media/password-spraying-detection-with-splunk-13.png" /></p><ul><li><strong>ComputerName 1</strong>: all events come from one machine</li><li><strong>LogName 1</strong>: only the Security log</li><li><strong>date_year, date_month, date_mday, date_hour 1 each</strong>: one day, one hour</li><li><strong>date_minute 6</strong>: about a 5-minute window</li><li><strong>EventCode 9</strong>: 9 types of events</li></ul><h4>Step 2: What happened, and how much?</h4><p>First I counted the events for each EventCode:</p><pre data-lang="spl"><code>index="bruteforce_windows"
| stats count by EventCode
| sort - EventCode</code></pre><p><img src="media/password-spraying-detection-with-splunk-14.png" /></p><p>Event codes are just numbers, so I pulled out the readable name from the TaskCategory line with rex:</p><pre data-lang="spl"><code>index="bruteforce_windows"
| rex "TaskCategory=(?&lt;category&gt;[^\r\n]+)"
| stats count by category EventCode</code></pre><ul><li>[^\r\n]+ means "everything up to the end of the line"</li><li>I grouped by both category and EventCode, because a successful logon (4624) and a failed logon (4625) have the same category, Logon. If I grouped by category only, the failures would hide inside the successes</li></ul><p><img src="media/password-spraying-detection-with-splunk-15.png" /></p><table><thead><tr><th><p><strong>EventCode</strong></p></th><th><p><strong>What it means</strong></p></th><th><p><strong>Count</strong></p></th></tr></thead><tbody><tr><td><p>4688</p></td><td><p>a program started</p></td><td><p>37</p></td></tr><tr><td><p>4689</p></td><td><p>a program closed</p></td><td><p>37</p></td></tr><tr><td><p>4624</p></td><td><p>an account logged in successfully</p></td><td><p>16</p></td></tr><tr><td><p>4634</p></td><td><p>an account logged out</p></td><td><p>16</p></td></tr><tr><td><p>4672</p></td><td><p>a login with admin-level rights</p></td><td><p>11</p></td></tr><tr><td><p>5140</p></td><td><p>a shared folder was opened over the network</p></td><td><p>3</p></td></tr><tr><td><p>5145</p></td><td><p>the server checked permissions on a shared folder</p></td><td><p>2</p></td></tr><tr><td><p><strong>4625</strong></p></td><td><p><strong>an account failed to log in</strong></p></td><td><p><strong>20</strong></p></td></tr><tr><td><p><strong>4776</strong></p></td><td><p><strong>the domain controller checked a password (here it was wrong)</strong></p></td><td><p><strong>20</strong></p></td></tr></tbody></table><h4>Step 3: What is normal here?</h4><ul><li><strong>4688 and 4689</strong>: 37 programs started and 37 closed. I questioned these because they happened seconds apart. When I looked closer, almost all of them were Splunk's own log-collection agent starting its helper programs every minute, run by the computer's own account. I learned that fast doesn't mean suspicious. I check what it is, who started it, and whether there is a regular pattern</li><li><strong>4624 and 4634</strong>: 16 logins and 16 logouts. They match, so people came and went</li><li><strong>4672</strong>: admin-level logins by system accounts, which is normal on a domain controller</li><li><strong>5140 and 5145</strong>: machines reading shared folders</li></ul><h4>Step 4: What doesn't fit?</h4><p>I wanted to see success and failure side by side, so I pulled out the Keywords value and made a matrix with chart:</p><pre data-lang="spl"><code>index="bruteforce_windows"
| rex "TaskCategory=(?&lt;category&gt;[^\r\n]+)"
| rex "Keywords=(?&lt;keywords&gt;[^\r\n]+)"
| chart count over category by keywords</code></pre><p>chart count over category by keywords puts the categories down the side and Audit Failure / Audit Success across the top. stats would give me a long list instead.</p><p><img src="media/password-spraying-detection-with-splunk-16.png" /></p><p>The only failures on the whole server were <strong>20 failed logons and 20 failed credential validations</strong>. Everything else succeeded.</p><p>These two numbers match because each login attempt was logged twice: once when the domain controller checked the password (4776) and once when the login failed (4625). So it is 20 attempts, not 40. That's also why I count by EventCode and not by the words "Audit Failure".</p><h4>Step 5: What could explain 20 failed logins?</h4><p>Before calling it an attack, I listed every possible explanation and what each one would look like in the logs:</p><table><thead><tr><th><p><strong>Possible explanation</strong></p></th><th><p><strong>What it would look like</strong></p></th></tr></thead><tbody><tr><td><p>A user forgot their password</p></td><td><p>one account, a few tries, then a success</p></td></tr><tr><td><p>An app or service using an old password</p></td><td><p>one account, failing at regular times</p></td></tr><tr><td><p>Password guessing</p></td><td><p>one or two accounts, many tries each</p></td></tr><tr><td><p>Password spraying</p></td><td><p>many different accounts, about one try each, from one source</p></td></tr></tbody></table><p>Each explanation leaves a different footprint, so my next questions were the ones that tell them apart.</p><h4>Step 6: Which accounts, and how many tries each?</h4><p>I used the 4776 events, because they have only one account name each (Logon Account:). The 4625 events have two Account Name lines, and the first one is just "-".</p><pre data-lang="spl"><code>index="bruteforce_windows" "credential validation"
| rex "Logon Account:(?&lt;account&gt;[^\r\n]+)"
| stats count by account</code></pre><p><img src="media/password-spraying-detection-with-splunk-17.png" /></p><p><strong>20 different accounts, and each one was tried exactly once.</strong></p><h4>Step 7: Did any of them succeed?</h4><p>I added the success or failure value next to each account:</p><p><img src="media/password-spraying-detection-with-splunk-18.png" /></p><p><br />Every one of the 20 attempts was an <strong>Audit Failure</strong>. I also checked the successful logons (4624), and none of these 20 accounts logged in successfully. The error code on every attempt was 0xC000006A, which means the username was real but the password was wrong.</p><p>The host column here is the domain controller that wrote the log, not the attacker</p><h4>Step 8: Where did it come from?</h4><p>In a 4776 event, the machine that sent the attempt is on the Source Workstation: line:</p><pre data-lang="spl"><code>index="bruteforce_windows" EventCode=4776
| rex "Logon Account:\s+(?&lt;account&gt;\S+)"
| rex "Source Workstation:\s+(?&lt;src_ws&gt;\S+)"
| stats count dc(account) as accounts by src_ws</code></pre><p>One machine, <strong>WIN-HOST-816</strong>, made all 20 attempts against 20 different accounts. The 4625 events show its IP address, <strong>10.0.1.15</strong>.</p><h3>What I concluded</h3><p>One machine inside the network, <strong>WIN-HOST-816 (10.0.1.15)</strong>, tried to log in to <strong>20 different accounts, once each, in 39 seconds</strong> (09:11:18 PM to 09:11:57 PM). Every attempt used a real username with a wrong password, and every attempt failed.</p><p>This is <strong>password spraying (T1110.003)</strong>, and it was <strong>unsuccessful</strong>.</p><p>Because the attempts came from a computer inside the network, the attacker most likely already had control of WIN-HOST-816. As an analyst, I would investigate that machine, check which user was logged in on it, and make sure account lockout, strong passwords and multi-factor authentication are in place.</p><h3>MITRE ATT&amp;CK mapping</h3><table><thead><tr><th><p><strong>Item</strong></p></th><th><p><strong>Details</strong></p></th></tr></thead><tbody><tr><td><p><strong>Tactic</strong></p></td><td><p>Credential Access (TA0006)</p></td></tr><tr><td><p><strong>Technique</strong></p></td><td><p>Brute Force (T1110)</p></td></tr><tr><td><p><strong>Sub-technique</strong></p></td><td><p>Password Spraying (T1110.003)</p></td></tr><tr><td><p><strong>Platform</strong></p></td><td><p>Windows (Active Directory)</p></td></tr><tr><td><p><strong>Evidence in my logs</strong></p></td><td><p>20 failed logons (4625) and 20 failed credential checks (4776) from WIN-HOST-816: 20 different accounts, 1 try each, in 39 seconds</p></td></tr><tr><td><p><strong>Detection</strong></p></td><td><p>MITRE's detection idea for this is DET0487: Distributed Password Spraying via Authentication Failures Across Multiple Accounts.

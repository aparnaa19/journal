# Credential stuffing with splunk
display_title: What is credential stuffing
skills: Credential stuffing detection, Log analysis, Splunk SPL, Regex field extraction, XML log parsing, Windows Security event analysis, Threat hunting, Incident investigation, MITRE ATT&CK mapping
tools: Splunk Enterprise, Splunk SPL, Windows Security Event Logs, MITRE ATT&CK

**Brute Force Credential Stuffing Detection with Splunk**<p>In this lab:</p><ul><li>loaded Windows XML logs and set up my own source type so Splunk could read them</li><li>counted the event types and worked out who logged in and who failed</li><li>found the source IP behind the failures and checked every machine it touched</li><li>measured how fast it happened and checked whether any attempt worked</li></ul><h3>What is credential stuffing</h3><ul><li>Credential stuffing (MITRE <strong>T1110.004</strong>) is when an attacker takes usernames and passwords that leaked from somewhere else and tries them on a new system</li><li>It is done by a script, so it is fast and goes across many places at once</li><li>I think of it as having a bag of stolen keys and trying them on every building in town, hoping one fits</li></ul><h3>About the logs</h3><p>The logs come from Splunk's public attack_data repository on GitHub (datasets/attack_techniques/T1110.004). They were recorded in a test Windows network called attackrange.local on 22 March 2023.</p><p>The file has 112 events, and every event is written in XML, which is how Windows really stores its events. The machine that wrote each event is in the &lt;Computer&gt; tag.</p><h3>Getting the logs into Splunk</h3><h4>Step 1: I uploaded the file</h4><p>I used <strong>Settings → Add Data → Upload</strong> and picked windows-security.txt.</p><p><img src="media/credential-stuffing-with-splunk-1.png" /></p><h4>Step 2: The default source type did not work</h4><p>With the default source type, the preview showed a warning icon, and the date was today's date (11/15/26) instead of the date in the log.</p><p><img src="media/credential-stuffing-with-splunk-2.png" /></p><p>So Splunk could not find the time inside the event, and I had to tell it where to look.</p><h4>Step 3: I looked at the raw file first</h4><p>I opened the file in Notepad to see what one event looks like.</p><p><img src="media/credential-stuffing-with-splunk-3.png" /></p><ul><li>Each event is one long line that starts with &lt;Event and ends with &lt;/Event&gt;</li><li>The time is inside the line, written as SystemTime='2023-03-22T20:25:38.778428300Z'</li><li>Every detail is written as &lt;Data Name='TargetUserName'&gt;AR-WIN-DC$&lt;/Data&gt;. The name is in the tag and the value is between the tags. Splunk will not turn these into fields on its own yet, so I have to pull them out</li></ul><p>I learned that XML is just the same information as the text logs I used before, with tags around each piece.</p><h4>Step 4: I told Splunk how to read the time</h4><p>Under <strong>Timestamp → Advanced</strong>, I set a prefix and a format:</p><p>Timestamp prefix:  SystemTime='</p><p>Timestamp format:  %Y-%m-%dT%H:%M:%S.%9N%Z</p><p><img src="media/credential-stuffing-with-splunk-4.png" /></p><ul><li>The prefix tells Splunk that the time starts right after SystemTime='</li><li>%Y-%m-%d is year-month-day, and T is the letter T between the date and the time</li><li>%H:%M:%S is hour:minute:second, and %9N is the fraction of a second</li><li>%Z is the Z at the end, which means UTC time</li></ul><p>I also set <strong>Event Breaks</strong> to <strong>Every line</strong>, because each event is exactly one line</p><p><img src="media/credential-stuffing-with-splunk-5.png" /></p><p>Now every event has the right date (3/22/23) and there are no warnings.</p><h4>Step 5: I created an index and finished the upload</h4><p><img src="media/credential-stuffing-with-splunk-6.png" /></p><p>I made a new index called <strong>bruteforce_win_xml</strong>. I kept it separate from my other indexes, because this data is XML and my other data is plain text.</p><p><img src="media/credential-stuffing-with-splunk-7.png" /></p><p><img src="media/credential-stuffing-with-splunk-8.png" /></p><p>The host field shows my laptop's name, because host is the machine that uploaded the file. The real machine names are inside the logs.</p><h4>Step 6: The fields were still not readable</h4><p>I searched index="bruteforce_win_xml" and got 112 events. The events were there, but the field list on the left was full of useless fields.</p><p><img src="media/credential-stuffing-with-splunk-9.png" /></p><p>So I went to <strong>Settings → Source types</strong>, opened my source type and added one more setting under <strong>Advanced</strong>:</p><p>KV_MODE = xml</p><p><img src="media/credential-stuffing-with-splunk-10.png" /></p><p>KV_MODE=xml tells Splunk: this data is XML, so read the tags as fields. After that, fields like Event.System.EventID and Event.System.Computer appeared.</p><p><img src="media/credential-stuffing-with-splunk-11.png" /></p><h3>Investigating the logs</h3><h4>How I approached it</h4><ol><li><strong>What am I looking at?</strong> How much data, which machines, what time</li><li><strong>What is normal here?</strong> What makes up most of the activity</li><li><strong>What doesn't fit?</strong> Failures, rare accounts, sudden bursts</li><li><strong>Follow the thread.</strong> Who, from where, to which machines, did it work?</li><li><strong>So what?</strong> Is it an attack, and what should be done?</li></ol><h4>Step 1: What am I looking at?</h4><p>From the field panel in Step 6 of the loading section:</p><ul><li><strong>112 events</strong> in total, all from 22 March 2023, over about a minute</li><li><strong>Event.System.EventID 2</strong>: only 2 types of events</li><li><strong>Event.System.Computer 51</strong>: events written by 51 different machines</li></ul><p>I learned to click a field name in the panel to see its values, instead of reading the long raw events.</p><h4>Step 2: What are the two event types?</h4><p>I pulled out the EventID with rex and counted it:</p><pre data-lang="spl"><code>index="bruteforce_win_xml"
| rex "&lt;EventID&gt;(?&lt;event_id&gt;[^&lt;]+)"
| stats count by event_id</code></pre><ul><li>&lt;EventID&gt;(?&lt;event_id&gt;[^&lt;]+) means: find the text &lt;EventID&gt;, then save everything up to the next &lt; into a field called event_id</li><li>[^&lt;]+ is the XML version of my old [^\r\n]+. It stops at the next tag instead of the end of the line</li></ul><p><img src="media/credential-stuffing-with-splunk-12.png" /></p><table><thead><tr><th><p><strong>EventID</strong></p></th><th><p><strong>What it means</strong></p></th><th><p><strong>Count</strong></p></th></tr></thead><tbody><tr><td><p>4624</p></td><td><p>an account logged in successfully</p></td><td><p>60</p></td></tr><tr><td><p><strong>4625</strong></p></td><td><p><strong>an account failed to log in</strong></p></td><td><p><strong>52</strong></p></td></tr></tbody></table><h4>Step 3: Who logged in, and who failed?</h4><p>I added the username (TargetUserName) and counted by both fields:</p><pre data-lang="spl"><code>index="bruteforce_win_xml"
| rex "&lt;EventID&gt;(?&lt;event_id&gt;[^&lt;]+)"
| rex "&lt;Data Name='TargetUserName'&gt;(?&lt;user&gt;[^&lt;]+)"
| stats count by event_id user</code></pre><p><img src="media/credential-stuffing-with-splunk-13.png" /></p><ul><li><strong>4624 (success)</strong>: the AR-WIN-xx$ accounts, AR-WIN-DC$ (37 times) and ANONYMOUS LOGON (10 times). Names that end in $ are machine accounts, which log on to the domain controller all the time</li><li><strong>4625 (failure)</strong>: only one account, <strong>Administrator, 52 times</strong></li></ul><p>This is what doesn't fit: a real account (Administrator) shows up only in the failures, and never in the successes. Nobody else failed at all.</p><h4>Step 4: Where did the attempts come from?</h4><p>I extracted the source IP (IpAddress) and the logon type, and counted again:</p><pre data-lang="spl"><code>index="bruteforce_win_xml"
| rex "&lt;EventID&gt;(?&lt;event_id&gt;[^&lt;]+)"
| rex "&lt;Data Name='TargetUserName'&gt;(?&lt;user&gt;[^&lt;]+)"
| rex "&lt;Data Name='IpAddress'&gt;(?&lt;src_ip&gt;[^&lt;]+)"
| rex "&lt;Data Name='LogonType'&gt;(?&lt;logon_type&gt;[^&lt;]+)"
| stats count by event_id user src_ip logon_type</code></pre><p><img src="media/credential-stuffing-with-splunk-14.png" /></p><ul><li>All 52 Administrator failures came from <strong>10.0.1.30</strong></li><li>Each AR-WIN-xx$ machine account logged on from its own IP (10.0.1.15 to 10.0.1.23), so that is normal</li><li>::1 is the machine talking to itself (loopback), and fe80::... is an IPv6 link-local address built from the machine's MAC address. Both are internal, so the only outside source here is 10.0.1.30. A - means the event had no source address</li><li>The 10 <strong>ANONYMOUS LOGON</strong> successes also came from <strong>10.0.1.30</strong>, with logon type 3 (over the network)</li></ul><p>At first I called the anonymous logons normal, but I checked the IP and they came from the same machine as the failures. I learned not to call a success normal until I check where it came from.</p><h4>Step 5: Which machines did 10.0.1.30 touch?</h4><p>I added the machine name (Computer) and filtered to the attacker's IP:</p><pre data-lang="spl"><code>index="bruteforce_win_xml"
| rex "&lt;EventID&gt;(?&lt;event_id&gt;[^&lt;]+)"
| rex "&lt;Data Name='TargetUserName'&gt;(?&lt;user&gt;[^&lt;]+)"
| rex "&lt;Data Name='IpAddress'&gt;(?&lt;src_ip&gt;[^&lt;]+)"
| rex "&lt;Data Name='LogonType'&gt;(?&lt;logon_type&gt;[^&lt;]+)"
| rex "&lt;Computer&gt;(?&lt;computer&gt;[^&lt;]+)"
| where src_ip="10.0.1.30"
| stats count by event_id user src_ip logon_type computer</code></pre><p><br /><br /><img src="media/credential-stuffing-with-splunk-15.png" /></p><p><img src="media/credential-stuffing-with-splunk-16.png" /></p><ul><li>There were 62 events from this IP: 52 failures plus 10 anonymous logons</li><li>The 52 failed logons landed on <strong>51 different machines</strong>, about 1 try on each (one machine got 2). The whole file has only 51 machines, so every machine in the file was tried</li><li>The 10 anonymous logons landed on ar-win-2 to ar-win-10 and ar-win-dc</li></ul><p>I learned that Windows logon events have no destination IP. The destination is the machine that wrote the event, which is the &lt;Computer&gt; tag. Each machine logs its own failures, so I count machines with Computer.</p><p>This is why a normal per-machine alert would miss it: each machine saw only one failed login, which looks harmless. The attack only shows when I group by the account across all machines.</p><h4>Step 6: How fast was it?</h4><p>I added _time to the table to see when each event happened:</p><p><img src="media/credential-stuffing-with-splunk-17.png" /></p><ul><li>The anonymous logons were at about <strong>16:25:14.7</strong></li><li>The failed Administrator logons were right after, from <strong>16:25:15.0</strong> onwards</li><li>Many failures share the exact same time, 16:25:15.072</li></ul><p>So the whole thing took about <strong>1 second</strong>. No person types that fast, and identical timestamps mean the attempts were fired together. It is a script.</p><h4>Step 7: Did it work?</h4><p>In the Step 3 table, Administrator has <strong>0 successful logons (4624)</strong>. Every Administrator attempt was a 4625. So the attack did not get in with that account, at least in this log.</p><p>The anonymous logons are a different thing. They are not a stolen password. They are connections with no credentials at all (a null session), which attackers use to look around a Windows machine. So this IP touched the network in two ways, and I would not ignore either.</p><h3>What I concluded</h3><p>One machine inside the network, <strong>10.0.1.30</strong>, made 10 anonymous network logons and then, in about 1 second, tried the <strong>Administrator</strong> account <strong>once on each of 51 machines</strong>. All 52 attempts failed.</p><p>This is a <strong>credential stuffing style attack (T1110.004)</strong>, and it was <strong>unsuccessful</strong> for the Administrator account.</p><h3>What I would do next</h3><ul><li><strong>Contain:</strong> isolate 10.0.1.30 from the network, because an attacker most likely controls it. It is an internal address, so someone or something inside was already compromised</li><li><strong>Investigate:</strong> find out what 10.0.1.30 is and who owns it. Check what that machine did before 16:25, and check whether it made any successful logons to other accounts</li><li><strong>Check the anonymous logons:</strong> look at what those 10 sessions accessed, such as shared folders (EventIDs 5140 and 5145 in my last lab)</li><li><strong>Protect Administrator:</strong> rename or disable the default Administrator account, use a long unique password, turn on multi-factor authentication, and turn on account lockout</li><li><strong>Reduce anonymous access:</strong> restrict null sessions on the machines so they cannot be used to look around</li></ul><h3>MITRE ATT&amp;CK mapping</h3><table><thead><tr><th><p><strong>Item</strong></p></th><th><p><strong>Details</strong></p></th></tr></thead><tbody><tr><td><p><strong>Tactic</strong></p></td><td><p>Credential Access (TA0006)</p></td></tr><tr><td><p><strong>Technique</strong></p></td><td><p>Brute Force (T1110)</p></td></tr><tr><td><p><strong>Sub-technique</strong></p></td><td><p>Credential Stuffing (T1110.004)</p></td></tr><tr><td><p><strong>Platform</strong></p></td><td><p>Windows (Active Directory)</p></td></tr><tr><td><p><strong>Evidence in my logs</strong></p></td><td><p>52 failed logons (4625) for one account, Administrator, from one IP (10.0.1.30), across 51 machines, in about 1 second</p></td></tr><tr><td><p><strong>Detection idea</strong></p></td><td><p>count how many different machines see failed logons for the same account in a short time</p></td></tr><tr><td><p><strong>Mitigations</strong></p></td><td><p>M1036 Account Use Policies, M1032 Multi-factor Authentication, M1027 Password Policies</p></td></tr></tbody></table>

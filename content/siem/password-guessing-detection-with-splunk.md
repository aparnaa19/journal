# Password guessing detection with splunk
display_title: Password guessing detection with splunk
skills: Log analysis,Threat hunting,SPL,Regex field extraction,Detection engineering,Sigma rule writing,Detection validation,MITRE ATT&CK mapping
tools: Splunk Enterprise,Sigma,sigma-cli,MITRE ATT&CK,LogHub OpenSSH dataset

**Brute force Password guessing attack detection with splunk:**<br /><br />I set up Splunk and loaded 2,000 real SSH logs from a Linux server. In this part, I use Splunk to find where the attack is coming from, what the attacker was trying to do, and whether they got in. Then I turn what I found into a Sigma rule, so the same attack can be caught automatically next time.</p><p>In this part:</p><ul><li>found the attacker IPs using SPL searches</li><li>checked which accounts they were going after and whether any login worked</li><li>wrote a Sigma rule for the attack</li><li>converted it into Splunk SPL with sigma-cli and checked that it catches the same attackers</li></ul><p><strong>What is brute force</strong></p><ul><li>Brute force is when an attacker keeps trying passwords until one works</li><li>One type of brute force is: <ul><li><strong>Password Guessing (T1110.001)</strong>: many passwords tried on the same account. I think of it as trying lots of keys on one door</li></ul></li></ul><p><img src="media/password-guessing-detection-with-splunk-1.png" /></p><p><strong>Finding the attack</strong></p><p><strong>Step 1: I looked at only the failed logins</strong></p><p>Every failed SSH login has the words “Failed password” in it, so I searched for that:</p><pre data-lang="spl"><code>index="bruteforce_openssh" "Failed password"</code></pre><p>This gave me 520 events out of 2,000. So about a quarter of all the log lines are failed logins, which is already suspicious.</p><p> </p><p><img src="media/password-guessing-detection-with-splunk-2.png" /></p><p> <strong>Step 2: I pulled out the attacker’s IP</strong></p><p>I wanted to count failures per IP, but Splunk had not pulled out the IP as its own field. It was stuck inside the text, like ...from 183.62.140.253 port.... So I used rex to pull it out:</p><pre data-lang="spl"><code>| rex "from (?&lt;ip&gt;\d+\.\d+\.\d+\.\d+)"</code></pre><ul><li>from is the word that comes just before the IP</li><li>(?&lt;ip&gt;...) saves whatever matches into a new field called ip. I learned that this name is my own choice, it doesn’t come from the log</li><li>\d+\.\d+\.\d+\.\d+ is the shape of an IP address: numbers with dots in between</li></ul><p>When I clicked the new ip field, one IP stood out straight away: <strong>183.62.140.253 caused 55% of all failed logins (286)</strong>.</p><p>I have to remember that regex is case-sensitive. I first typed From with a capital F, and it matched nothing, because the log says from.</p><p><img src="media/password-guessing-detection-with-splunk-3.png" /></p><p><strong>Step 3: I counted the failures per IP</strong></p><pre data-lang="spl"><code>| stats count by ip</code></pre><p>This turned 520 events into a table with one row per IP. There were 23 IPs. Most of them had only 1 to 3 failures, which looks like normal people mistyping. A few had much more.</p><p>I used stats here instead of just reading the popup, because I can add more steps after stats, and I can save it.</p><p> </p><p><img src="media/password-guessing-detection-with-splunk-4.png" /> </p><p><strong>Step 4: I kept only the noisy IPs</strong></p><pre data-lang="spl"><code>| where count&gt;10</code></pre><p>A real user might get their password wrong a few times, but not more than 10. With this filter, only <strong>6 IPs</strong> were left. These are the attackers.</p><p><img src="media/password-guessing-detection-with-splunk-5.png" /> </p><p> </p><p> </p><p><strong>Analysing the intent</strong></p><p>Finding the IPs was not enough. I wanted to know what they were trying to do and whether it worked.</p><p><strong>Which accounts were they going after?</strong></p><p>I pulled out the username too. Some lines say for root from... and others say for invalid user guest from... (invalid means the account doesn’t exist). One rex had to handle both:</p><pre data-lang="spl"><code>| rex "for (invalid user )?(?&lt;username&gt;\S+) from"
| stats count by username, ip
| where count&gt;10
| sort - count</code></pre><ul><li>(invalid user )? means “skip these words if they are there”. The ? makes them optional</li><li>\S+ grabs one word, which is the username</li></ul><p>I learned that regex counts every space. When I shortened it to (invalid)?, all the invalid users disappeared, because the space and the word “user” were left behind.</p><p>Every high-volume attempt was on <strong>root</strong> or <strong>admin</strong>. Nobody was trying normal user accounts. The attackers wanted admin access.</p><p><img src="media/password-guessing-detection-with-splunk-6.png" /></p><p><br /><strong>Did anyone get in?</strong></p><p>A successful login says “Accepted password”. I searched for that from all 6 attacker IPs at once using OR:</p><pre data-lang="spl"><code>index="bruteforce_openssh" "Accepted password" ("183.62.140.253" OR "187.141.143.180" OR "103.99.0.122" OR "112.95.230.3" OR "5.188.10.180" OR "185.190.58.151")</code></pre><p>0 results. <strong>No successful login from any of the attacker IPs.</strong></p><p><img src="media/password-guessing-detection-with-splunk-7.png" /><br /></p><p><strong>What I concluded</strong></p><p>6 IPs ran an SSH brute force attack against this server. They only went after root and admin, and the worst one, 183.62.140.253, tried root 276 times. None of them got in, so the attack failed.</p><p>This is <strong>password guessing (T1110.001)</strong> and not spraying, because they made many attempts on a few accounts. Spraying would be a few attempts on many accounts.</p><p>If this was a real server, I would block these 6 IPs, turn off password login for root, use SSH keys instead of passwords, and add something like fail2ban to block IPs after a few failures.</p><p><strong>Turning it into a detection with Sigma</strong></p><p>My SPL searches found the attack once, by hand. But in a real SOC, nobody can search manually every day. A detection rule watches the logs automatically and alerts when the same thing happens again.</p><p><strong>What is Sigma</strong></p><ul><li>Sigma is a way to write detection rules in a simple YAML file that isn’t tied to one tool</li><li>A converter turns the same rule into Splunk, Elastic or Microsoft Sentinel searches</li><li>I think of it as writing a recipe in plain English, and a translator turns it into any language</li></ul><p><strong>The 3 parts of a Sigma rule</strong></p><ul><li><strong>Metadata</strong>: the name, level and MITRE tags. I think of it as the label on the box</li><li><strong>Detection</strong>: where to look and what to match. I think of it as the actual instructions</li><li><strong>Correlation</strong>: counts how many times the detection matched. It is written as a separate rule. Brute force needs this, because one failed login is not an attack, but hundreds are</li></ul><p><strong>Step 1: I wrote my rule</strong></p><ul><li>The first rule finds every “Failed password” line</li><li>The second rule counts them with event_count, separately for each IP (group-by: src_ip)</li><li>It alerts when one IP fails 10 or more times within 5 minutes (timespan: 5m, gte: 10)</li><li>I added the 5-minute window because 10 failures spread over a whole year is not an attack. Brute force is many failures in a short time</li></ul><p> <img src="media/password-guessing-detection-with-splunk-8.png" /></p><p><strong>Step 2: I converted it with sigma-cli</strong></p><p>sigma-cli is the official tool for converting Sigma rules. I installed it with Python and ran:</p><p>pip install sigma-cli pysigma-backend-splunk</p><p>sigma convert -t splunk --without-pipeline passwordguessing.yaml</p><ul><li>-t splunk means convert it into Splunk SPL</li><li>--without-pipeline means keep the normal Sigma field names, because there is no ready-made setup for Linux SSH logs</li></ul><p><img src="media/password-guessing-detection-with-splunk-9.png" /></p><p><strong>Step 3: I fixed the field names</strong></p><p>The converted search did not work on my data straight away:</p><ul><li>it searched a field called message, but my logs don’t have that field</li><li>it expected a field called src_ip, but my IP was still inside the text</li></ul><p>So I added my index, searched the text directly, and added my rex with the name src_ip:</p><pre data-lang="spl"><code>index="bruteforce_openssh" "Failed password"
| rex "from (?&lt;src_ip&gt;\d+\.\d+\.\d+\.\d+)"
| bin _time span=5m
| stats count as event_count by _time src_ip
| search event_count &gt;= 10
| sort - event_count</code></pre><p>I learned that this is normal. Real SOC teams set up their logs so the fields are already pulled out, and they use pipelines to match the field names automatically. My logs are raw, so I did it by hand.</p><p><strong>Checking that it worked</strong></p><p>The rule caught all 6 attacker IPs. 183.62.140.253 shows up in three 5-minute windows in a row: 16 + 141 + 129 = 286. That is exactly the number I found in my investigation, so the rule is working.</p><p><img src="media/password-guessing-detection-with-splunk-10.png" /></p><p><strong>Conclusion:<br /></strong></p><table><tr><td></td><td></td></tr><tr><td><p>Tactic</p></td><td><p>Credential Access (TA0006)</p></td></tr><tr><td><p>Technique</p></td><td><p>Brute Force (T1110)</p></td></tr><tr><td><p>Sub-technique</p></td><td><p>Password Guessing (T1110.001)</p></td></tr><tr><td><p>Platform</p></td><td><p>Linux (SSH)</p></td></tr><tr><td><p>Evidence in my logs</p></td><td><p>6 IPs with many “Failed password” attempts on root and admin</p></td></tr><tr><td><p>Detection</p></td><td><p>My Sigma rule (failed logins counted per IP in 5 minutes).
